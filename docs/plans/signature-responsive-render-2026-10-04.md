# 签名画像：响应式精绘与缩放

## 范围与实现

用户认可当前生产签名画效果，本阶段保留排布、着色数学和画序，解决精绘时主线程阻塞。普通笔迹的概览和局部高清渲染使用独立 Worker；场景模板只初始化传输一次，后续只发送尺寸和可视区域。取消只保留最新请求，切换作品和离开页面释放 Worker。不可用时回退到分片 Canvas；镂空排印继续使用已验证的分片路径。

同步和分片画笔复用同一生成器，模板准备、矢量准备、字体变体生成也按约 8ms 时间片让出主线程。新增真实阶段与进度提示，系统减少动效时停止旋转动画。缩放有轻快 / 清晰 / 精细三档，屏幕最长边分别上限 1280 / 2400 / 3200；下载仍使用作品快照及成图尺寸，调整预览档不影响文件内容。

后台模板预算 96MiB，单个输出最多 67,108,864 像素；染色缓存沿用 16MiB / 64 项。这些是局部资源限制，不代表所有设备的总体内存已认证。默认 GPU 预览未晋升。PNG 编码、项目恢复和镂空绘制仍有主线程操作。

## 失败与修复

- 仅主线程分片的首测仍出现 P95 256ms、最长约 852ms 的帧间隔。进一步移出普通笔迹栅格绘制。
- 初版 Worker 虽改善 P95，仍有一次约 2473ms 间隔。分析发现 GPU 绘制命令积压在最终读回；在 Worker 时间片之间读回一个像素排空队列。
- `willReadFrequently: true` 的软件栅格后端造成大量像素变化（通道最大差 52），拒绝采用；明确保持原栅格后端。
- 旧缩放合同只注入一次 context 失败，自动回退后自然恢复。改为持续阻断同尺寸候选的后台显示和兼容绘制，解除故障后仍必须恢复，像素门槛未放宽。

## 验证

冻结基线 `a7f219000beb884e8cd5d682f1ba0bf4ac97028c`。Edge / Chrome 各 20 场：两种笔迹 × 两种底色 × 染色 × 填色的 16 组合，同步、分片、分块和区域绘制 RGBA 与基线一致；普通笔迹的 Worker 对照同样零差。取消、真实 100 写法生成、三档缩放及 390px 无横向溢出通过。

真实生成使用 2K、16074 枚签名，减少动效环境的观测如下。它们是本机两次独立运行的响应观测，不能当作跨设备性能保证。

| 浏览器 | 帧数 | rAF P95 | 最大帧间隔 | 20ms 定时器最大间隔 |
| --- | ---: | ---: | ---: | ---: |
| Edge 154 | 644 | 18ms | 102.9ms | 80.9ms |
| Chrome 154 | 831 | 17.3ms | 146.6ms | 60.4ms |

Chrome 精绘中仍有三次大于 100ms 的帧间隔（111.4 / 146.6 / 121.9ms）；Edge 一次 102.9ms。加载反馈实际可见。改善显著，但“所有场景绝不卡”未被证明。

8K布局的区域缩放合同通过，实际区域 RGBA 零差，屏上画布未超过默认 2400 边长；持续失败时保留已生成作品，解除故障恢复高清显示。作品快照、PNG / SVG / JSON一致性、跨浏览器项目恢复和染色缓存回归按对应报告记录。产品 type-check、相关 ESLint、build 通过后提交。精简证据位于 [signature-responsive](../validation/2026-10-04/signature-responsive/)。
