# 聚散真实时间与输入调度

接续[图片后台阶段](./image-preview-background-2026-10-05.md)。图片已在后台完整绘制，但页面 `.15` 秒和工厂 `.25` 秒的时间截断，会把秒级完整帧的归位拉长。本阶段修正聚散时间与排队手势，继续保留原生场、正向字形、中文句序及原 RGB；高密度绘制吞吐仍未达到商业验收。

## 实现

- 聚散使用与指针事件同源的 `performance` 时钟。只有超过 `.25` 秒的聚散间隔走新分支：按最多 128 个真实事件的时间戳回放，用原生 `.05` 秒小步进推进 trail 场，同时推进原闭式阻尼弹簧。静止区间跳过无用 PDE，仍同步弹簧时钟；常规短帧和其它效果继续旧路径。
- 场补算约每 8ms 检查一次并让出执行权，可取消，页面区分“正在更新字符位置”和实际字符绘制。单次原生调用仍不能中途打断。大于 `1e9` 秒的异常时钟使用原有有界路径，避免浮点不前进；没有调整原生 `makeStudioInteraction` body。
- Worker 进度只接受当前任务、上一合法交互时钟对应的总间隔，以及严格递增的有限秒数和整数步数。字符绘制开始后，交互进度不能再重置 watchdog。兼容分段路径转发同样的阶段反馈。
- 图片聚散的新输入按原 30Hz 上限进入队列，绕过秒级完整帧的空闲节流；没有新输入且完整帧尚在绘制时，不用空闲动画更新覆盖已排队手势的时间。仍只保留一份正在绘制的完整帧和一份最新候选，恢复继续按真实时间推进。视频仍沿用视频调度预算。
- 已呈现 Canvas 的 `particlePeak` / `particleBytes` 来自该完整结果的真实统计。开发和生产合同用相同的位移门槛，不依赖 Vue 内部状态。全屏测试先等目标 Canvas 的完整初帧，触控同时验证可见变化和精确归位。

离线 HTML 共用工厂和真实聚散时钟，绘制仍同步；本阶段没有将 HTML 后台化。首页三保护源、Studio `.65/.38/.45`、FxButton、64 临时彩色图块预算和免费输出边界保持。未重启已停止的签名容量、视频 atlas、软件 tint/LUT 或 tile pool 调参。

## 实际失败与修复

1. 开发 R1 只等“活动”，读到了彩色模式第一个微弱完成帧。R2 增加真实完整结果和 `peak > .005` 等待后仍超时：后续 peak 仅 `.000164`，证明实际调度确有问题，不能以测试等待消除。排队快速手势被数秒后的空闲 tick 推进到几乎静止；上述输入优先与完整帧等待修正后，180 列彩色模式明显反馈并精确归位。没有降低 `.005` 门槛或列数。
2. 旧生产合同六模式归位通过，但手机全屏 60 秒精确归位超时。新全屏 Canvas 在异步初帧前已存在，旧函数立即读 `toDataURL()`；改为等真实完整、静止初帧后取基线。生产 Chrome 再次验证手机全屏 358×447、真实 1 down / 10 move / 1 up / 0 cancel、可见变化和相同 PNG，保持原 60 秒及逐像素门槛。
3. 开发 R3 六模式已通过，之后执行格式化触发开发热更新，后续暂停等待失败、Canvas 已不存在。该轮仅保留为局部证据，不当完整通过；最终改用稳定生产构建完成全流程，并固定源码 hash。
4. 最终数值合同 R1 的状态/Worker/取消都正确，但 1 秒补算只触发 5 次 20ms timer，因旧断言要求“超过 5 次”而失败；最大间隔实际 48.9ms。固定次数会惩罚更快完成。改为逐次验证每条 progress 后的排队 heartbeat 真能执行，并检查最大补算片段及 timer 间隔都小于原 200ms 上限。原失败保留，数值、强反馈及像素门槛未改；新合同在两浏览器通过。

## 验证与限制

证据归档在[聚散时钟验证目录](../validation/2026-10-05/glyph-particles-clock/)。Chrome 154.0.8037.57 / Edge 154.0.4258.53 的生产构建完整流程均通过：真实上传 180 列，六模式 `peak > .005`、可见变化、60 秒内 PNG 精确归位；桌面全屏自身及主预览精确归位、Worker 2→1；暂停环境仍可见交互且环境时间固定；减少动效静止并允许滚动；390px 编辑器、全屏、断网 HTML 三组真实触控可见变化/精确归位；HTML 零网络请求；本地短 WebM 使用 Worker、媒体时间前进；SPA 离页后 Worker 归零。

两浏览器算法合同使用 alpha-zero fixture，不能作画质/FPS证据：常规 30 帧状态与冻结 `b6eb80c` 完全相同，1/2/5 秒间隔与原生 `.05` 秒参考状态最大差 `0 / 8.73e-11 / 4.55e-13`；同步/分段状态及真实 Worker peak 零差；晚到输入 peak `.10895`；5 秒长间隔自然静止、可取消、异常巨大时钟有界。最终 Chrome / Edge 的 timer 最大间隔 93.9 / 63.7ms，补算片段最大 71.9 / 42.2ms；每条进度均能让排队 heartbeat 执行。两浏览器各 21 项 watchdog 虚拟故障通过，不用于真实性能结论。

最终两浏览器各 24 组 / 720 帧常规输入与冻结 v9 RGBA 相同，自然归位、原 indices/RGB、旧 trail、容量及 wrapper 通过。Chrome 图片后台 80 项冻结 RGBA、取消、最新候选、全屏/缩放/兼容恢复通过；两浏览器完整视频回归的 24 组冻结采样、18 组 Worker 绘制、六模式实播、暂停稳定、240 列 8 帧预解析/取消、全屏释放和 390px 兼容回退通过。Edge 超容量编辑器/HTML 输入零绘制且允许滚动。type-check、相关 ESLint、build 通过，既有 chunk、动态导入、stream 警告保留；短本地视频及 buffering 事件合同仍不代表所有长视频、用户编码或网络 stall 已验收。

这是一次真实页面操作和完整结果追踪的墙钟耗时，包含测试手势、读回及截图，不是隔离基准或 FPS。记录的 WebM 来自实际编辑器鼠标输入，捕获申请 30fps 不代表字符画完成 30fps；MP4 导出仍为环境动画快照。

Edge 同负载首次完整反馈：光影约 418ms，其余约 1.33–2.22 秒；手势开始至精确归位约 5.36–7.45 秒。两段实际编辑器 VP9 录像经原生解码核验均为 571×713，分别 33 / 31 个编码帧；不把编码帧数当成每秒完成字符帧数。

归位时钟与手势呈现修复不等于逐字绘制已经实时。用户随后报告“正在绘制字符画”频繁出现，已复现静止零位移仍重复绘制及普通动效触发生成提示，接续独立修复；然后研究完整静态帧与局部动态重绘，须先独立证明透明度、六模式、画质与 RGBA 一致。本阶段没有接入该缓存。长视频/用户编码/真机、真实手写商业画质、原创素材与全部六方向目标继续，未部署、未宣布整体商业验收。
