# 分块超清 PNG 的无损编码核心 · 2026-10-07

用户要求下载放大后名字清晰，并指出整幅 SVG 后续渲染很卡。接续[后台 PNG](./signature-png-background-2026-10-07.md)，先验证无需巨型整幅 Canvas 的编码路径。**当前只是编码核心，尚未把正式签名作品的 16K 绘制或新导出入口接入页面；不据合成 PNG 称名字清晰度已经完成。**

## 实施与算法

`createPngRowEncoder()`接受连续 RGBA 条带，单条带最多512行，输出边最大16384。每行在无损 Sub/Up 预测中按残差绝对值选择；前一行跨条带保留，保证接缝不重置。Deflate `CompressionStream`持续输出标准 PNG IDAT，生成每块 CRC32、IHDR/sRGB/IEND。没有颜色量化、JPEG 转换、整幅 RGBA 数组或新第三方依赖。

编码运行在调用方 Worker，压缩流读写同时进行，避免反压死锁；间歇让出 Worker 事件循环。压缩结果以不可变 Blob 块收集，最终 Blob引用这些块；有512MiB压缩载荷预算、取消/不完整条带/尺寸错误拒绝及资源终止。此预算不等于浏览器进程内存上限，也不免除后续查看大 PNG 的解码内存。

## 验证和失败

Edge/Chrome各7种合成 RGBA：1×1、17×129、384×257、519×513、16384×33、17×16384、13112×16384。每项从 Worker 仅返回 Blob；独立 Python 标准库 zlib/CRC32 与 NumPy 逐行解码，核对完整尺寸、每一个 RGBA 通道、跨条带滤波、所有 CRC、流结束及无多余数据，全部零差。含非全透明/不透明 alpha和透明像素中的 RGB，不只看 PNG 头部。

每浏览器另验证4种非法尺寸、实际计算中取消、压缩预算超限、不完整文件、错误条带宽度，共8类拒绝。类型检查、相关 ESLint及构建检查随阶段证据记录。最初测试 Worker 的异步 import 前未接收初始化消息而等待；明确停止原验证进程，增加初始化队列后运行，未把该测试脚本错误认作产品编码错误。

13112×16384输入的完整RGBA为859308032字节，测试只同时提交128行、6713344字节条带，行工作缓冲209793字节；不是实际进程内存测量。该周期合成色图压缩约2.23MB，编码约11.72/12.14秒，**不能外推到复杂签名作品的文件大小或整幅绘制耗时**。公开精简记录见[验证结果](../validation/2026-10-07/signature-png-stream/summary.json)，原始合成PNG仅留ignored `test-results/`。

## 后续产品合同

1. 直接从当前完整签名/固定排版绘制条带，再编码；不把旧PNG拉大、不改变已认可的普通PNG、生成快照或项目恢复。
2. 放大笔迹先以实际模板/可复现字体配方检查来源。字体辅助可以研究同一配方的高分辨率绘制，但不能替换原模板后声称像素未变；上传/手写来源的细节上限与轮廓保留单独验证。不重启已停止的墨量/正负拼贴等实验。
3. 先可操作同尺寸对照和真实名字原大裁片，再接超清PNG入口、后台进度/取消/回退/重开；整幅SVG不作为默认浏览方案。另评估切片浏览，防止后期查看把一张巨图再次完整渲染。

当前16K名字清晰度、低内存真机和实体印刷尚未通过，六方向商业目标继续。
