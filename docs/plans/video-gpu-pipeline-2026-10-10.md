# 动态字符画：预解析、GPU 绘制与资源预算

## 本阶段结论

目标是用户可以等待预解析，完成后保持选定画质，播放、环境动效和悬停交互流畅。当前完成了绘制瓶颈确认与隔离 GPU 原型；没有完成全品质、高清或 4K 持续 60fps 的正式接入。

实际入口 `src/lib/art-engine/index.ts` 已有 WebGL2，但 expressive、cinematic、多种高级 hover 和还原栅格会走 Canvas。预解析缓存能复用采样结果，仍会在每次交互中计算字符几何、生成彩色字块并逐字绘制。把帧率选项设为 60 不会消除这些成本；单纯延长解析时间也不能预先算完用户未来的指针轨迹。

本次候选保留原生 Canvas 工厂的动效、交互与字形几何计算，把最终逐字绘制收集为实例缓冲，再用共享字形图集和一次 GPU 实例化绘制输出。它仍在 CPU 上计算交互与逐字颜色，不是完整 GPU 求解器。候选仅支持经典栅格，明确拒绝 softwareRaster/超采样，不能用它替换用户的“还原”画质。

## 实测范围与失败

[原始耗时记录](../validation/2026-10-10/video-gpu/feasibility-r3.json)包含 18 个路径和原始样本，[开发素材清单](../validation/2026-10-10/video-gpu/manifest.json)保留源 ID 和哈希。同一仓库肖像、微软雅黑、1440×960/DPR1、Edge 154、Intel UHD 770；三模式 density/color/phrase，80/180/400 列分别配长边 720/1920/3840。固定 wave/cinematic/trail、时间步长 1/60 和指针轨迹。只测离屏 renderer，包括 GPU finish 或 Canvas 单像素读取，不包含实际屏幕呈现、视频解码、Worker 通信与完整页面。

GPU 有效热样本每路径仅 10 帧：80 列 density P95 9.9ms、phrase 9.3ms；80 列 color P95 25.3ms，已超 16.67ms。180 列三模式 P95 分别 23.6/42.7/29.4ms，全部未过 60fps 绘制预算。400 列 density P95 78.4ms；color/phrase 分别因 312.8/112.5ms 单帧触发早停，仅冷样本。即使绘制低于 16.67ms，也还需要为解码、场计算、UI 和合成保留预算。

Canvas 九个路径全部在首帧超过 100ms 后早停。报告保留了该单值，但其中的 P50/P95 字段不能解释为热态统计；不计算“稳定提升倍数”。GPU 与 Canvas 的最后截图时间不同，不能当作逐像素一致性对照。已目视检查低清 GPU 的单色及原色主体和正向字形；未因此宣称六模式、中文句序、透明输出或还原品质一致。

r1 无足够进度与停止保护，人工核对归属后终止；r2 在高列彩色路径耗时过长，没有完整报告；r3 加入逐路径落盘、100ms 早停和 240 秒截止，完成记录。没有付费评审、模型调用或用户素材上传。数据集只是一个已有开发素材，无训练/留出集泛化、Pareto 品质选择或跨设备性能结论。

研究脚本是 `sandbox/ascii-optimizer/scripts/video-gpu-feasibility.mjs`，候选是 `sandbox/ascii-optimizer/engine/video-gpu-20261010-r1/batch-gpu.ts`。原始冻结副本和 PNG 留在本地 sandbox，不批量提交。已有 r3 记录保持原样；提交前仅改善脚本的路径检查、异常截止清理、复跑元数据和候选的类型引用，未据此重新生成 r3 耗时。

收尾检查：脚本语法、相关 ESLint、候选 strict TypeScript、素材清单结构、文档链接和原始报告字节一致性通过。独立类型检查首次遇到 TypeScript 6 的配置选择要求，添加 `--ignoreConfig` 后通过。此阶段没有修改正式 `src/`，没有为研究文档重跑产品 build。

## 实施顺序与验收关卡

1. **建立一致性基线。** 冻结同一帧、字体、时间和完整指针路径，比较 Canvas 与候选的源字形索引、颜色、透明度、几何和输出。保留静态零强度、拖尾、中文与透明背景反例。经典、精细、柔和、还原分别设合同；GPU 图集需要处理字格边缘采样串色及面积滤波差异。画质失败时继续修候选，不把高品质偷偷降成经典。
2. **把解析与交互绘制分开。** Worker/WebCodecs 按源时间一次生成紧凑的 glyph index、源色、alpha 和必要采样数据。字形图集以字体/字号/字重/字符集为键复用。视频帧数据上传只发生在源帧改变时，屏幕交互帧主要更新时间、指针和共享场。将 CPU 逐字字符串颜色及几何循环逐步替换成数值缓冲、字段纹理和 shader，同时逐项核对原生场语义。
3. **分清源帧率和显示帧率。** 原片 24/30fps 按真实时间读取；60Hz 交互可在同一源帧上连续渲染，不能把重复帧称为新增视频细节。解码、解析、播放、hover 时钟独立且以媒体时间同步，暂停视频时仍按现有合同允许交互。隐藏标签页、离屏、取消和换素材停止无用工作。
4. **缓存分块落盘。** 不把全片的完整 RGBA/Canvas/GPU texture 同时常驻。按时间分页，将紧凑解析块存到 OPFS 或 IndexedDB，预取邻近页，用 LRU 淘汰过期页；共享字形图集。分别预算 JS 数据、派生视频、GPU texture/buffer、编码器和临时复制。当前 96MiB 预览缓存与 GIF 输出上限仅覆盖各自阶段，不等于浏览器全部内存上限。配额不足、驱逐、断点恢复及重解析都需要用户可理解的状态。
5. **接真实编辑器与输出。** 先验证经典六模式，再逐档解决还原栅格和高级 hover；同一渲染合同接普通预览、全屏、项目恢复及导出。处理 context loss、纹理尺寸限制和低 GPU；离线 HTML 打包同版本工厂并有可用回退。视频导出使用确定的媒体时间逐帧编码，允许比实时慢，避免要求导出和预览同时占满资源。
6. **以设备验收后交付。** 在实际页面采集呈现帧间隔 P50/P95、超过 50ms 的卡帧、输入延迟、冷解析、热播放和峰值内存；连续运行至少 10 分钟并检查释放后增长。覆盖当前集显、独显、低端设备与真实手机，再声明可达到的列数、长边和效果组合。截图、离屏 renderMs 和帧率下拉框都不能替代持续呈现验收。

每一步先形成可复现小目标与失败记录，再独立提交推送。正式推广前补 source-grouped 多素材开发/留出集，按画质、性能、内存硬约束选择品质优先/均衡/资源优先路径。当前单素材实验不足以进行此选择。

## 用户与服务端的边界

默认“省资源”保持视频/GIF 低清和低帧率；用户明确选择“等待完整画质”后显示解析进度、预计缓存需求、取消与恢复。目标是在支持的设备上维持选定画质，若超预算则说明可用范围并让用户选择，不能无提示降低画质。预览和导出使用独立任务状态；高质量慢导出可以继续等待，不阻塞页面操作。

认证、验证码、价格、付费权益、素材访问权限和付费渲染额度由后端判断。本地采样与 GPU 绘制处理用户素材，不签发权限或模拟业务成功。若后续确有云端渲染需求，再由后端创建有幂等键的任务、校验身份/归属/额度、限制并发并排队，支持取消、失败重试、结果授权下载和过期清理；浏览器只展示服务器任务状态。

目前不新增云队列、Docker 集群或收费服务，不自动上传用户媒体。本地主库尚缺 commerce 表及 auth_version，已有 health UP 和 MCP 连接不能证明完整商业后端可用；迁移遵守兄弟后端仓库的受控建库脚本。验证码的模拟发送已关闭，参考[渠道修复](./auth-channel-authority-2026-10-10.md)。

本阶段关联的[GIF 与缓存修复](./gif-preview-resource-2026-10-10.md)已经正式提交；探索页自然滚动、全屏居中及主题切换均在该阶段完成。本 GPU 候选仍处于 sandbox，尚未替换正式渲染器。
